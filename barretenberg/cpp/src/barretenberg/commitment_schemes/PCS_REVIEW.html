1. What a backend actually plugs into

TransparentHonk<Pcs> is the shell. Everything above the commitment layer — arithmetization, the Ultra relation set, memory records, log-derivative lookups, the grand product, sumcheck, the Fiat–Shamir schedule — is shared verbatim with the production prover. A backend supplies only a config, a commitment key, a commitment type, and a prove/verify pair for one multilinear opening.

After sumcheck at challenge u, the PCS receives 41 claims over 36 committed columns:

Pi(u) = vi for i = 1…36   and   shift(Pj)(u) = wj for j = 1…5
where  shift(P)[i] := P[i+1]   and   N = 2n
Unshifted claims. Ordinary multilinear evaluations of each committed column at the sumcheck challenge.
Shifted claims. The by-one shift of five columns. Every backend needs its own way to open these without a second commitment — §1.2 below. This is where new backends most often go wrong.

1.1 One array, two bases

A polynomial is one dense array of length N, read simultaneously as a multilinear evaluation table and as univariate coefficients. The stride-2 Lagrange fold serves both readings at once, which is why fifteen schemes can share one data layout:

a′[j] = (1 − α) a[2j] + α a[2j+1]
A(X) = Ae(X2) + X Ao(X2) ⇒ A′(Y) = (1−α)Ae(Y) + αAo(Y)
Even half — as a multilinear, this is the X1 = 0 restriction; as a univariate, the even coefficients.
Odd half — the X1 = 1 restriction, and the odd coefficients.
Univariate split. The same array read as a degree-<N polynomial.
The folded univariate. One loop, both readings, no basis conversion — Gemini, WHIR, Mercury, Vela and SwitchFold all rely on this.

1.2 Three ways to handle the Honk shift

(a) Univariate division — Gemini/Shplemini, WHIR, Mercury, Vela

The univariate twin of the shift is exactly P(X)/X, an exact division because the shift contract forces P[0] = 0. Mercury multiplies its fold identity through by X so the verifier can keep using the unshifted commitment:

B(X) = Q(X) (Xb − α) + X gB(X) ,   Q(X) := X qB(X)
The unshifted polynomial — the verifier already holds its homomorphic commitment, so nothing new is committed for the shift.
The quotient, pre-multiplied by X. This absorption is the trick: it moves the X−1 off the committed side.
Remainder, ζ-scaled at check time. Precondition: P[0] = 0, asserted at prove time (finding §3.7).

(b) Rank-2 tensor decomposition — Ligero, SwitchFold, Hyrax, KZH2, Dory

The shifted-eq weight vector is not a tensor, so it cannot be fed to a tensor-query PCS directly. But it is a sum of exactly two tensors, which is enough:

Q′ = b ⊗ shr(a) + shr(b) ⊗ (aC−1 e0)
index j = rC + c,  Q′r,c = brac−1 (c ≥ 1),  Q′r,0 = br−1aC−1 (r ≥ 1),  Q′0,0 = 0
Main term. Reuses the row direction b unchanged and pairs it with the column shift — one extra combined row.
Carry term. Handles the wrap from column 0 to the previous row. It costs a second combined row, of which only entry 0 is ever used.
The dropped corner. Because this entry is zeroed structurally, contract (b) needs no zero-constant-term precondition — unlike (a).

KZH3 extends this to rank 3: the shift of the flattened index k = (i1d2+i2)d3+i3 crosses two boundaries, adding a second carry. Verified term by term.

(c) Successor-kernel closed form — Pedersen IPA, Dory's scalar side

The IPA fold collapses the whole weight vector to one scalar. For the plain eq tensor that is a product; for the shifted eq vector it telescopes, and the derivation is the pretty one in the suite — split on the position of the lowest set bit of the index, because that is exactly the bit that i − 1 clears:

∑k ∏j<k uj · (1 − uk) · mk · ∏j>k ((1 − uj) + ujmj)
Bits below k are all set in i−1 (the borrow filled them), so each contributes its uj factor.
Bit k is cleared in i−1 — one (1−uk) factor.
The IPA fold multiplier for that bit position. In the lo/hi round schedule this is the round challenge inverse in reverse order — the subtlety that §4.2's rewrite had to get right.
Bits above k are unconstrained, so they contribute the ordinary eq-fold factor. The verifier never touches a shifted commitment.

2. The two most elegant constructions in the suite

Mercury's Laurent identity — extracting an inner product from a constant term

Mercury has to prove two inner products. Instead of two arguments it batches them into a single Laurent-polynomial identity, whose constant term is exactly the quantity of interest:

∑k γk (pk(X)rk(1/X) + pk(1/X)rk(X)) = 2∑k γkck + X S(X) + X−1S(1/X)
An inversion-symmetric product. Its coefficient at Xk is ∑i≥k(piri−k + pi−kri) — verified coefficient by coefficient against accumulate_ip_terms.
The inner products, doubled. This is the only place the constant term can come from — which is the whole point.
The witness polynomial, structurally constant-term-free. For any S whatsoever, this pair contributes nothing at X0. That is why no degree bound on S is needed — and correspondingly none is implemented. A reviewer looking for a missing degree check here would be wrong.

Vela — the evaluation the verifier is never sent

Vela reads the multilinear claim as the constant coefficient of a Laurent product, then exploits its inversion symmetry to compress the opening into a single auxiliary polynomial. The striking part is the last step: one of the four evaluations is never transmitted.

H(X) = fv(X) · Tr(1/X) ,   [X0]H = y  ⇔  the claim holds
D(X) = H(X) + H(1/X) − 2y = X h(X) + X−1h(1/X)
w1 = z ( g(z)Tr(1/z) + g(1/z)Tr(z) − 2Y − z w0 )
The Laurent twin. Tr(X) = ∏k((1−rk) + rkX2k); its inverse-variable form has eqi(r) at exponent −i.
The claim, encoded as a constant coefficient.
The residual, whose constant coefficient is 2([X0]H − y) — zero exactly when the claim is true.
Symmetry pays off. Because Dk = D−k, the whole residual is carried by one ordinary polynomial h.
The evaluation that is never sent. The verifier derives h(1/z) from the identity being proved, then uses it in the two-point opening. A lying prover's recovered value is inconsistent and the opening fails. The constraint is enforced by making the verifier compute, rather than check, the value.

Deviation from the paper, forced by bb's SRS: the two-point check would need [τ2]2, and bb publishes only [1]2, [τ]2. The degree-2 vanishing is therefore linearized at one further challenge — one extra G1 element. Sound: the linearized check at a random ζ drawn after Cq forces the identity.

4. Correctness findings

No soundness break was found in any backend's protocol logic. Every Fiat–Shamir ordering is correct (each challenge is drawn strictly after the messages it must bind). Seven findings; the material ones:

§3.1 — Four backends ship deliberately insecure setups. KZH2 and KZH3 sample their own trapdoors in-process; CHOPIN fixes τY = 2 and publishes [τY]2 = 2[1]2; Dory uses Γ2,i = siG2 with public si, which destroys AFGHO binding.

All four are labelled @warning Test-only and the honest-prover cost is unaffected — that is the point of the shortcut. But it means those four rows in the table are performance models, not security claims. Dory's fix is mechanical (hash-to-G2); CHOPIN's needs a bivariate ceremony that does not exist.

§3.2 — The Reed–Solomon query count rests on a disproved conjecture. RSCodePolicy returns t = ⌈λ/r⌉, the up-to-capacity rule. Crites–Stewart (2025/2046) disproved the conjecture it rests on, replacing δ ≤ 1−ρ−η by Hq(δ) ≤ 1−ρ−η. WHIR ships a repaired preset (+1 query, ~2% proof at BN254); Ligero and SwitchFold do not.

Half of this closed while the review was being written. The shared, distance-parameterized query hook landed — QuerySegment plus query_plan, with Brakedown using the provable rule and Bolt returning two segments for its piecewise-distance code. What remains: RSCodePolicy still has no repaired variant, and SwitchFold is not wired to the hook.

§3.3 — The Ligero-family proximity test rides on the opening point being a challenge. Ligero, SwitchFold and Hyrax use a single combination for two jobs: the same eq-weighted combined rows serve as the proximity test and the evaluation extraction. Classical Ligero/Brakedown run a separate test with a uniformly random vector, precisely because the eq tensor is not uniform.

This is sound here — tensor-structured randomness supports proximity gaps (Diamond–Posen, 2023/630) — but only when u is uniformly random and drawn after the commitments. Inside TransparentHonk it is. But the standalone API accepts an arbitrary caller-supplied point, and nothing in the signature, doc-comment or README says otherwise. A user of a pluggable-PCS product who opens at a public, fixed point gets no proximity guarantee at all.

§3.4 — Brakedown's base-case code is not MDS. The parity block is a Vandermonde in the coefficient basis, so the codewords are (coeffs(f), f(p0), …) — not a Reed–Solomon code at all. A nonzero f of degree < k has at most k−1 roots, so the provable distance is only 1 + max(0, parity − (k−1)) — which at k = 32, parity = 24 evaluates to 1, against d = 25 for a true MDS [56, 32] code.

The actual distance is probably fine. But Brakedown's whole value proposition is a distance that holds with provable failure probability 2−100, and the recursion consumes the base case's distance as a hypothesis. Fix: a Cauchy matrix, which is superregular and therefore genuinely MDS. One function, no cost change.

5. Efficiency: one defect ran through the whole suite

Every non-production backend opened by forming the ρ-combination of the ~41 claims — and every one of them wrote it as a serial nested loop, while production Gemini does the identical work through the parallel add_scaled_batch:

for (each claim) {
    for (size_t k = 0; k < n; ++k) { array[k] += rho_power * column[k]; }
    rho_power *= rho;                    // ~10.7M serial multiply-adds at 2^18
}

The backends could not reuse add_scaled_batch because it takes Polynomial operands and they hold std::vector<fr>. utils/batch_accumulate.hpp now supplies the vector-backed counterpart: one parallel pass over the output range with the terms looped inside each chunk, so writes stay disjoint and each output cache line is touched once per chunk rather than once per term.

Separately, the IPA backend was not using MSMs at all — its round loop performed 2N individual elliptic-curve scalar multiplications. Switching from even/odd to lo/hi halves (the classical Bulletproofs split) makes both cross-term operands contiguous, so each is a single Pippenger call.

Prover cost, ratio to the KZG baseline — log scale

Two results worth calling out. CHOPIN now proves faster than the KZG baseline while producing a 9.2 KiB proof against KZG's 13.3, and Vela's prover penalty for the smallest proof in the suite drops from 1.70× to 1.18×. Both were previously read as "pay prover time for proof size"; that trade is now much weaker.

Measurement methodology, and its limits. The machine was shared with another build session for part of the window, so absolute wall-clock is not comparable across runs. Every figure is a ratio to the KZG baseline measured in the same run. Ligero is the control — its code is untouched, so its movement (0.70 → 0.72×, +3%) is the noise floor. A later run under contention moved the control by 26% and was discarded rather than reported. Proof bytes and verifier work are unchanged by every fix.

Quantified but not implemented

  • SwitchFold's weight tables do 4× more work than necessary. Two eq factors at the constants 0 and 1 zero three quarters of every tensor — and those zeros are still computed, as multiplications by zero, then added. Restricting the build to the live quarter is worth ~195 ms at 218.
  • Dory's verifier lives in GT exponentiation — 41 square-and-multiply exponentiations of 254 bits. Cyclotomic squaring (~2×) plus a bucket-method GT multi-exponentiation (~4×) would move the 362 ms verifier a lot. Neither primitive exists in bb's fq12.
  • IPA can go further still — production ipa.hpp fuses round pairs and uses 127-bit short challenges on top of what was applied here.
  • Ligero's three verifier FFTs are correctly left alone — direct evaluation at the queried positions is not a win at the current shape. Recorded so it is not re-investigated.

A user who selects "Mercury" and gets a non-zk proof has a security failure, not a performance trade. The work is also not uniform, which matters for scoping:

  • Pairing/KZG family (Mercury, Vela, CHOPIN) — bounded-degree blinders plus SRS degree slack. Each paper gives the design, but each opens a different set of auxiliary polynomials, so each needs its own argument.
  • √N / N1/3 families (KZH2, KZH3, Hyrax, Dory) — the combined rows are sent in the clear. Hiding them is a structural change, not a wrapper.
  • Hash family (Ligero, SwitchFold, Brakedown, Bolt) — WHIR's recipe transfers in shape, but the clear-text rows and descent messages each need their own masking design and query-count accounting.

The structural good news. WHIR's zk design lives entirely inside the PCS — extra blinding coefficients in a region the claim does not see, salted Merkle leaves, and one batched mask polynomial — with no change to TransparentHonk or anything above it. That is evidence that "zk-capable" can be a property of the backend rather than of the proof system, which is exactly what a pluggable design needs. It just has to be implemented thirteen more times.

7. Can a Noir frontend expose a selectable PCS backend?

What the evidence says yes to

The architecture question is answered, and answered positively. Fifteen schemes spanning four trust models, three commitment types (Merkle digest, vector of G1, vector of GT) and three different shift constructions all sit behind one shell, unmodified above the PCS. The Fiat–Shamir schedule, relation parameters and sumcheck are genuinely shared with the production prover, so backends do not fork the proof system.

And the abstraction keeps absorbing new structure rather than fighting it: a linear-time code, a code-policy parameterization, and a piecewise-distance query plan for a sketched-LDPC backend all landed during this review, and none required a change above the PCS layer. An abstraction that survives contact with genuinely different cryptography is the thing you cannot fake.

A roadmap that would make it shippable

  • Phase 1 — make the honest set small and real. Productize three backends, not fifteen: KZG (has zk, has recursion, is the default), Vela (smallest proof, fastest verifier, and a real ceremony already available since it reuses bb's existing KZG key), and WHIR (has zk, transparent, recursion designed). Gate the other twelve as research backends. This converts the zk gap from "13 backends" to one — Vela — which is a scoped piece of work rather than a programme.
  • Phase 2 — factor out the cross-cutting concerns. Finish the query rule; add a masking interface to the Pcs concept so the shell can require zk; make the opening-point precondition unrepresentable by construction; own parameter derivation at BN254.
  • Phase 3 — widen, only for backends that clear the Phase-2 bar. Best next candidates: CHOPIN (now the fastest prover in the pairing corner, if a bivariate ceremony is solvable), SwitchFold, Mercury.
  • Phase 4 — the frontend. Only here does the Noir-side work become the bottleneck rather than the cryptography.

The one-sentence answer. Yes, the product is possible — the pluggable architecture is already built and validated across fifteen schemes — but what exists today is a research bench, not a backend menu: the gap is not architecture, it is that thirteen of the fifteen backends have no zero-knowledge, four have no real setup, and fourteen have no recursive verifier.
